# Brain Command Architecture

Obsidian Brain 0.55.0 replaces a historically small but increasingly ambiguous command surface with one explicit command architecture across MCP, CLI, direct automation and Python.

## What changed

Every operation now has one dot-separated identity such as `artefact.create`, `vault.check` or `brain.upgrade`. The selected-Brain application owns 86 typed commands; 78 are eligible for granular MCP projection. Machine-global operations remain in a separate 23-command launcher catalogue. The two authorities compose discovery presentation without merging semantics.

MCP exposes one tool per eligible command (`artefact.create`, `vault.check`, and so on). CLI 2 uses the matching noun/verb grammar (`brain artefact create`, `brain vault check`). `command.py` and typed Python share the same sealed request, application executor, structural result and authority boundary.

## Why it is better

Agents no longer need to infer nested discriminators or recover opaque union schemas. Each tool owns one predictable semantic operation, and `command.list` / `command.describe` provide the exact installed schema, example, safety requirements, projection eligibility and availability. The catalogue—not docs, adapters or tests—is the semantic inventory.

The architecture also preserves the Brain's execution planes. Bootstrap, portable and managed dependency tiers are ordered; locality and providers are independent. An adapter cannot silently provision dependencies, elevate authority, switch Brains or hand execution to a different owner.

## Safer effects and upgrades

All projections preserve a structural result that distinguishes success, known partial effects, no-effect failure and unknown mutation outcome. Effect-bearing calls record bounded receipts. Unexpected mutation loss is never replayed merely because a process disappeared.

The 0.55.0 cutover replaces Brain Core, command catalogue, proxy, launcher, CLI and installer as one compatible set. Upgrade preflight requires a complete local registry and exact acknowledgement of every other local Brain affected by the global CLI replacement. A failed transaction either proves the previous set was restored or keeps recovery material and reports uncertainty.

## Migration

The upgrade transaction converts exact historical built-in profiles to cumulative catalogue-derived reader (37), contributor (63), maintainer (76), operator (85) and administrator (86) application-command sets; MCP projects their eligible 37, 63, 74, 77 and 78-command subsets. Custom profiles expand only aggregate authority they explicitly held and gain `invocation.read` only when receipt recovery requires it. Unknown or malformed authority blocks the migration before writes. There is no runtime compatibility mapping.

After upgrade, restart MCP clients once if the old live proxy reports `proxy_restart_required`. Update agent instructions to begin with `session.start` and use command discovery rather than remembered aggregate names.

## Deliberate exclusions

Remote Brain transport, authentication, staging and gateway hosting are not implemented here. The local architecture creates the clean application and launcher boundary that the child remote-gateway design can build on without reproducing the removed interface ambiguity.
